## 2. Firestore `leads` 文件結構

### 共用頂層欄位

| 欄位 | 說明 |
|---|---|
| `type` | `booking` / `group_class` / `franchise` / `cooperation` |
| `name`, `phone`, `email` | 主要聯絡資訊（`email` 可能為 `null`） |
| `storeId` | Firestore `stores` 文件 id。**只有 booking 有值**，其餘為 `null` |
| `sourcePage` | 來源頁路徑，如 `/booking`、`/group-booking` |
| `sourceChannel` | booking 專用＝使用者勾的「得知管道」join 成字串 |
| `message` | 使用者留言／備註 |
| `payload` | 各表單自己的欄位（見下） |
| `status` | `new` / `contacted` / `scheduled` / `completed` / `cancelled` |
| `internalNote` | 後台內部備註 |
| `createdAt`, `updatedAt` | Firestore Timestamp |

### `payload` — booking

```
gender, birthDate, line,
filledBySelf(boolean), relationship, bookerName, contactPhone,
hasMedicalCondition(boolean), medicalConditionNote,
preferredTime(string[]), paymentMethod,
exerciseGoals(string[]), exerciseGoalOther,   ← ⚠️ 恆為 null，見下方說明
sources(string[]),                 ← 使用者自填「得知管道」，長度恆為 1
utm{}, formVariant, company, leadSource
```

**三個會被誤解的欄位：**

| 欄位 | 實際行為 |
|---|---|
| `exerciseGoalOther` | **恆為 null**。前端在送出前就把「其他」併進 `exerciseGoals` 成 `其他: xxx`，request body 根本沒有這個 key。`preferredTime` 的「其他」也是同樣併法 |
| `sources` | 得知管道已改**必填單選**，但刻意仍以長度 1 的陣列存（後台、CSV、通知信全部照陣列寫）。有第二層時值是 `選項: 細項`，冒號後一個半形空格，見 `composeReferral()` |
| `filledBySelf` | 存的是**布林值**，不是中文字串。所以前端把「親友代填」改名為「他人代填」（2026-10-02）不會讓新舊名單在後台與 CSV 裂成兩種寫法 |

**前台的必填規則（2026-10-02 業主調整後）：**

- `email` 是**選填**。有填才驗格式；後端本來就是選填（沒有 email 就不寄客戶確認信）。
  ⚠️ 成功畫面那句「並寄送 Email 通知你」要跟著條件顯示，否則對沒留信箱的人是空頭承諾。
- 同意事項（`agreeToTerms`）在得知管道選「參觀」或「電話詢問」時**非必填**——
  那兩種來源代表學員已經到店或與同仁通過電話，條款現場說明過了。
  它只是前端的送出閘門，**沒有進 payload**，所以改必填條件不影響後端與名單。
- 「他人代填」會展開三個必填欄位（與學員的關係／預約者姓名／方便聯繫的電話）。
  ⚠️ 那個展開條件是用中文字串比對的，**改字面時有兩處要一起改**（`v-if` 與驗證）。
  只改下拉選項的話會變成：欄位不出現、驗證卻要求必填 → 表單送不出去又看不到錯在哪。

### `payload` — group_class

```
gender, ageRange,
isFillerSelf('是'|'否'), fillerName, relationship,
course, store(完整字串「南京店｜台北市…」), storeName(「｜」前的店名),
preferredTime(string), experience, medicalHistory,
source(string[]),                  ← 使用者自填「得知管道」
note,
utm{}, formVariant, company, leadSource
```

> ### ⚠️ booking 與 group_class 的欄位命名差異（最容易寫錯的地方）
>
> | 概念 | booking | group_class |
> |---|---|---|
> | 得知管道 | `sources`（複數） | `source`（單數） |
> | 是否本人填寫 | `filledBySelf`（boolean） | `isFillerSelf`（`'是'`/`'否'`字串） |
> | 代填者姓名 | `bookerName` | `fillerName` |
> | 健康狀況 | `hasMedicalCondition` + `medicalConditionNote` | 單一字串 `medicalHistory` |
> | 偏好時段 | `preferredTime`（陣列） | `preferredTime`（字串） |
> | Email | 選填 | **必填** |
> | 分店 | `storeId`（Firestore id） | `store`/`storeName`（字串，`storeId` 恆 null） |

### `payload.utm`

`{ source, medium, campaign, content, term, referrer, landingPage }` — 由 `composables/useUtm.ts` +
`plugins/utm.client.ts` 於進站時擷取 `utm_*` 存 sessionStorage，表單送出時附上。
**只給 Google Analytics 對帳用**，與下面的「活動來源」是兩套。

## 3. 三種「來源」欄位，各司其職（勿混用）

| # | 欄位 | 來自 | 用途 |
|---|---|---|---|
| ① 活動來源 | `payload.company`＋`payload.leadSource` | 網址 `?v=` / `?src=` | **後台名單分析主依據**（清單「來源」欄、篩選、CSV） |
| ② GA 追蹤 | `payload.utm.*` | 網址 `utm_*` | 給 Google Analytics；後台另有 UTM 欄位顯示 |
| ③ 使用者自填 | booking `payload.sources`／團課 `payload.source` | 表單**必填單選** | 「你從哪裡得知我們」問卷結果 |

`payload.formVariant` ＝ `?v=` 的原始值（辨識用）。
`leadSource`（如 `Facebook`）與 `utm.source`（如 `facebook`）重複是**刻意的**，後台篩選只讀 `leadSource`。

## 4. 廠商變體表單（`?v=`）

設定驅動，**加廠商＝加一段設定、不改頁面程式**。未知的 `?v=` 自動 fallback 成 `default`（不會壞）。

| 表單 | 設定檔 |
|---|---|
| `/booking` | `config/bookingVariants.ts` |
| `/group-booking` | `config/groupClassVariants.ts` |

**變體 key 兩邊刻意取同名**（`abbott`、`nanshan`），同一檔廠商活動可同時發兩條連結，
後台用同一組「公司／來源」篩選對得起來。

🔴 **但團課那邊目前只剩 `default`。**`config/groupClassVariants.ts` 的 abbott 與 nanshan
已於 2026-09-11 依業主要求刪除（整段還在，是註解掉的）。booking 那邊仍有
abbott / gigabyte / nanshan 三個。所以現在**發不出成對的團課連結** ——
舊的 `/group-booking?v=abbott` 會 fallback 成一般團課表單，名單不帶 company 與 leadSource。
要同時發兩條，得先把被註解的那段還原。下面那張能力表是「介面支援」，不代表現在有變體可用。

| 能力 | booking | group_class |
|---|:--:|:--:|
| `hero{badge,title,titleHighlight,subtitle,checklist,ctaText}` | ✅ | ✅ |
| `hideSources` 隱藏得知管道 | ✅ | ✅ |
| `company` / `leadSource` | ✅ | ✅ |
| `lockStoreId` 鎖分店（id/slug/name 命中） | ✅ | — |
| `lockStore` 鎖門店（門店字串開頭比對） | — | ✅ |
| `lockCourse` 鎖課程 | — | ✅ |
| `allAgesFree` 全齡免費 | ✅ | — （團課不分齡計價） |

鎖定欄位時，該欄位會從「可選」變成唯讀橘色卡片。
`?src=` 會覆蓋變體預設的 `leadSource`，同公司多來源共用一個變體。

## 5. 寄信（`server/utils/email.ts`）

送出後**一律寄兩封**，皆為非阻塞（`.catch` 記 log，失敗不影響表單回應）。

### 5-1 管理者通知信 `sendLeadNotification(data)`

- 收件人：Firestore `settings.emailRecipients`（逗號分隔，後台 `/admin/settings` 可改；現為 lkkwellness@gmail.com）。
  `settings.emailOnNewLead` 關閉時整個跳過。
- 主旨：`【練健康】新{表單類型}表單【{company}】- {姓名}`
- 有 `company`/`leadSource` 時，標題下方多一條橘色「活動來源」橫幅。
- 內容依 `type` 展開對應欄位；**「分店」列標題與頁尾後台連結會依 type 切換**
  （團課＝「上課門店」／連 `/admin/group-classes`；其餘＝「選擇分店」／連 `/admin/leads`）。

### 5-2 填單人確認信

| 表單 | 函式 | 版型 |
|---|---|---|
| booking | `sendBookingConfirmation()` | **sections 分區塊**：學員資料／填表人資料／健康狀況／預約資訊 |
| group_class | `sendGroupClassConfirmation()` | **sections 分區塊**：學員資料／填表人資料／健康狀況／報名資訊 |
| cooperation | `sendCooperationConfirmation()` | 簡易 details 條列 |
| franchise | `sendFranchiseConfirmation()` | 簡易 details 條列 |

四者共用底層 `sendFormConfirmation()`，文案在 `formConfirmationConfig`（subject/title/greeting/message/closing）。
團課的 closing 內含 LINE 官方帳號 `@201fzruh` 連結（團課要靠 LINE 排梯次）。

**業主既有決定（勿改回）：**
- 確認信**不標活動來源**（company/leadSource 只進管理者信與後台）。
- booking 的付款方式標示以**使用者實際勾選的 `paymentMethod`** 為準，不用年齡推算
  （50 歲以上若自己選臨櫃付款，信上就顯示 $500）。帶 `company` 的全齡免費活動則整行不顯示。

### 5-3 SMTP

環境變數 `SMTP_HOST/PORT/USER/FROM` + secret `SMTP_PASS`（Gmail App Password）。
改 secret 後**必須重新 rollout** 才生效。

## 6. 後台名單頁

| 頁面 | 讀取 | 可存取角色 |
|---|---|---|
| `/admin/leads` 客戶預約 | `type=booking` | admin（全權）／`custom`（看 permissions 有沒有勾到這頁）／editor・store_staff・sales |
| `/admin/group-classes` 團課預約 | `type=group_class` | 同上 |
| `/admin/cooperation` 合作表單 | `type=franchise` + `type=cooperation` | 同上 |

⚠️ 權限模型已經不是純角色。`utils/adminAccess.ts` 多了 `custom` 角色，
   以 `permissions` 勾選清單逐頁判斷；`editor` / `store_staff` 走的是完整存取。
   所以 **`store_staff` 進得去這三頁**，只是名單會被 `storeId` 過濾
   （而團課的 `storeId` 恆為 null，所以他看不到團課名單 —— 見下方已知限制）。

三頁共用 API：`GET /api/admin/leads?type=<type>`、`PATCH /api/admin/leads/{id}`（改 `status` / `internalNote`）。

### 版型（leads.vue 與 group-classes.vue 已對齊）

- 右上「匯出 CSV」
- 單排可搜尋下拉篩選（`components/SearchableSelect.vue`）＋已套用 chips＋清除全部＋筆數
  - 共同：搜尋（姓名/電話/Email）、日期區間、狀態、公司、來源、UTM 來源、UTM 活動
  - 客戶預約另有：分店（來自 Firestore `stores`）
  - 團課預約另有：門店、課程（**選項從現有名單自動蒐集**，因團課門店不是 Firestore store）
- 可排序表格（姓名/學員、分店/門店、狀態、時間），狀態下拉即時 PATCH
- 詳情彈窗：分區塊顯示全部欄位＋活動來源 chips＋UTM chips＋內部備註（可存檔）

**刻意的設計決定（勿改回）：**
- 「公司」與「來源」是**兩個獨立篩選**，不要合成一個下拉。
- **不提供「UTM 媒介」篩選**（區隔性低；資料仍存 payload、詳情與 CSV 看得到）。

🔴 **「本月」一定要用台北時間算。**原本是 `new Date(y, m, 1)`，取的是**伺服器本地時區**
   的月初 —— Cloud Run 跑在 UTC，等於台北時間當月 1 號早上八點，
   **每月 1 號 00:00–07:59 送出的名單全部被當成上個月**。
   2026-10-02 業主回報「本月預約體驗顯示 10 但表單有 12」，漏的正是 04:44 與 05:07 那兩筆。
   已改用固定 UTC+8 位移換算（台灣 1979 年起沒有日光節約時間，固定位移是精確的）。
   ⚠️ 這個 bug **在本機永遠驗不出來**（開發機就是 Asia/Taipei），要 `TZ=UTC node ...` 模擬。

⚠️ `composables/useLeadStatus.ts` 的 `leadTypeLabels` 曾經漏掉 `group_class`，
   而 `getLeadTypeLabel()` 找不到就回傳 type 本身 —— 後台「最近名單」會把原始字串
   `group_class` 直接印在畫面上。四種 type 都要在那張表裡有一筆。

## 7. 已知限制 / 待辦

1. **`/api/admin/leads` 只抓最新 100 筆再在記憶體篩 type**（`limit(100)`）。
   名單累積後，較舊的名單、以及量少的類型（團課、合作）會被 booking 洗掉看不到。
   → 名單量起來後要改成 **Firestore 端 `where('type','==',type)` + 分頁**（需建複合索引）。
2. **`store_staff` 角色看不到團課名單**：該角色過濾條件是 `lead.storeId === session.storeId`，
   而團課的 `storeId` 恆為 `null`。要開放需另用 `payload.storeName` 比對。
3. **全部表單皆無 reCAPTCHA / Turnstile**。
4. **寄信 fire-and-forget、無重試與告警**：SMTP 失敗只會 `console.error`，通知信靜默遺失。
5. **`?src=` 未在程式強制**，一致性只靠本文件與 `docs/廠商表單網址規範.md` 的紀律。
6. **團課課程價格寫在三處**（不是兩處）：
   - `pages/group-booking.vue` 的 `courses`（表單下拉）
   - `pages/group-booking.vue` 的 `courseCards`（頁面上方的課程介紹卡，三張各有 price）
   - `server/api/leads/group-class.post.ts` 的 `COURSE_PRICES`（確認信用）
   **改價要同步三處**。只改前兩處，使用者報名前最先看到的那三張卡會留著舊價格。
7. ~~後台的「醫師／院所」清單已經是死的~~ **2026-10-02 已清掉**（panel、
   `DEFAULT_DYNAMIC_OPTIONS`、公開端點、兩支 admin 端點共五處）。
   現在 `/admin/settings` 只維護「社群平台」與「實體活動」兩份清單。
   ⚠️ Firestore 的 `settings/referralOptions.doctor` **刻意留著不刪** ——
   沒有程式讀寫它了，刪它要動業主的正式資料又沒有好處。
